Choosing a minimal agent setup for DocsMind

Short answer: one main agent, one sub-agent (Change Analyzer), and five tools. Most of the “agent” should be deterministic code, with the LLM used only where judgment is needed.

Your single-pass architectures vary because the LLM is doing two jobs at once: finding candidates and judging them. Split those.

The Change Analyzer pipeline

  1. Deterministic candidates. Extract both documents into structured segments (id, page, section, text). Align by headings, then diff. The count is stable because no LLM is involved. This is your recall backbone.
  2. Cheap triage. A small model classifies each diff as formatting noise, a real change, or ambiguous. Most hunks resolve here.
  3. Verification loop per candidate, with a budget. For each real or ambiguous change, the agent must produce a quote and location from both versions. Code checks that the quotes exist verbatim in the extracted text. No matching quote means no change, which removes hallucinations. Cap the loop (e.g. 6 calls) and escalate only on failure.
  4. Coverage ledger. Every segment of A and B must end up as unchanged, changed, added or removed. If any segment is unaccounted for, the run isn’t done. This catches missed changes and makes the result checkable.
  5. Stable output. Temperature 0, canonical ordering by document position, and IDs derived from the segment IDs.

Minimal tools

  • extract(doc): layout-aware, handles multi-column, cached. Escalates to another parser or a page image when quote verification fails. That is what your 16-call cases are really doing, so build it in.
  • diff(A, B): deterministic alignment and diff.
  • search(doc, version, query) and read_segment(id): exact plus semantic search for going deep.
  • verify_quote(doc, quote): pure code, no LLM.
  • fetch_changelog: bounded, one or two attempts.

Changelog research

Check the document’s own revision history first, since it’s free. Only then do one bounded web lookup. Treat the result as a cross-check, not ground truth: every changelog entry should map to a detected change, and each unmatched entry triggers a targeted search of the documents. Its columns rarely match yours, so map it into your schema rather than copying it. This costs little and can catch what the diff missed.

Cost control

  • Cache extraction and embeddings per document version.
  • Use the strong model only for ambiguous candidates.
  • Set hard per-change and per-run budgets, and report any change that can’t be verified within them as “unresolved” instead of guessing.

DocsMind routing

DocsMind detects a compare-versions intent and hands off to the Change Analyzer. Everything else (Q&A, semantic search) stays as it is. You don’t need separate judge or refiner agents, because the verification step is mostly code.

Claude responded: You don't need a separate researcher agent.

You don’t need a separate researcher agent. Make it an optional, gated tool inside the Change Analyzer’s pipeline.

Why not a separate agent

  • It’s a single lookup with a clear output (a changelog table or nothing), not a reasoning loop. An agent adds a context handoff, extra tokens and another place to fail.
  • It’s a cross-check, not part of the core. The diff and verification loop must give the same correct result with or without it.
  • Keeping it out of the analyzer’s reasoning prevents the changelog from biasing the analysis. Use it only to confirm findings and to flag mismatches.

Gate it so closed-system documents never trigger a web search

  1. Internal first: check for a revision history, change table or version notes inside either document. This is free and works for closed systems too.
  2. Web only when there’s a public signal: a known public standard or vendor, a version string, a public URL in the metadata, or a user flag like “public document.” Otherwise skip it and log “no external changelog searched.”
  3. Hard limits: one or two search attempts, one fetch, and a size cap. If nothing is found, continue without it.

For your company documents, the web step simply never runs, so it costs nothing. The internal revision history check and the diff plus verification loop carry the work.

Implementation

Expose it as one tool, find_changelog(doc_metadata), that returns either a normalized table or not_found. The Change Analyzer calls it only if the gate passes. If you later find a document family where this is high-value, you can promote it to its own sub-agent. Until then it doesn’t earn one.
